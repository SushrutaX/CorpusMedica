## Project Summary (Facts to include)
- Project name: Corpus Medica.
- Goal: open-source medical AI platform, model-agnostic, modular workflow.
- Primary workflow: upload scan -> choose model -> run segmentation -> view results.
- Frontend: Vite + React + TypeScript, UI logic in App.tsx/App.css (no heavy UI framework).
- Backend: FastAPI, in-memory jobs, MONAI bundles for segmentation.
- Auth: Django + Postgres with Developer/Admin/User roles.
- Storage: uploads and outputs persisted on disk; results served via API.

---

## Segmentation Module (Detailed Facts)
- Models are served by the backend and fetched by the frontend for selection.
- Segmentation runs are created via /api/segment and tracked by job_id.
- Jobs transition through queued, running, done, or error.
- Jobs are stored in memory (Python dict keyed by job_id).
- Job IDs are generated with uuid4.
- Results are retrieved via /api/results/{job_id}.
- Results include status, model_id, saved_path, metrics, and outputs.
- Outputs include mask_path and report_path placeholders or actual files.
- Segmentation uses MONAI bundle inference where available.
- Inference outputs are written to /data/outputs/{job_id}/.
- Frontend polls results every ~1s and animates status changes.
- Run button is enabled only when upload and model selection are complete.
- Frontend presents metrics and download links once status is done.
- CPU and GPU configurations are supported via docker-compose variants.
- Weights are stored locally for reproducible runs.

## Report Analysis Module (Detailed Facts)
- Report analysis is exposed via /api/reports/analyze.
- Reports can be ingested from text or extracted from files on the backend.
- A parsing service standardizes report fields for downstream reasoning.
- Risk engine creates structured summaries and flags from report content.
- Groq-based explanations can be used when GROQ_API_KEY is configured.
- Frontend renders structured results with readable sectioning.

## Chatbot Module (Detailed Facts)
- Chatbot endpoint: /api/chat (POST).
- Health endpoint: /api/chat/health.
- Stats endpoint: /api/chat/stats.
- RAG uses Qdrant for vector storage and SentenceTransformer for embeddings.
- Gemini model provides final response generation.
- Chat requests include query, history, and top_k.
- Backend trims history and limits top_k for performance.
- Knowledge base indexing is done in the background on cold start.
- When index is empty, responses are generated without sources.
- Sources list includes file path and relevance score when available.

## 2D Slices Viewer (Main Page)
- 2D slices are fetched from /api/uploads/slice.
- Axis options: sagittal, coronal, axial.
- Slice index and channel are provided by the frontend.
- Backend normalizes slice data and applies colormaps.
- Supported colormaps include grayscale, bone, hot, cool, viridis.
- Backend returns a PNG image for each slice.
- Frontend animates slice changes with smooth transitions.

## 3D Volume Viewer (Main Page)
- Volume files are served by /api/uploads/volume-file.
- Backend returns NIfTI files (or extracted channels).
- Frontend renders volumes with a WebGL-based renderer.
- Transfer functions map voxel intensity to color and opacity.
- User can orbit, zoom, and pan the volume.

## Workspace (2D + 3D)
- Workspace mode extends 2D slices and 3D volume/mesh into a dedicated layout.
- The 3D workspace can use both volume and mesh views.
- 2D workspace supports slices with controls for axis, index, and colormap.
- Workspace is designed for clinical review and deep inspection.
- UI includes tool shelves, adjustable panels, and layout controls.

## 3D Mesh Pipeline (Detailed Facts)
- Mesh endpoint: /api/uploads/mesh.
- Mesh generation uses marching_cubes from scikit-image.
- Input volume is downsampled by step parameter for speed.
- Iso threshold can be absolute or normalized when between 0 and 1.
- Mesh output is PLY (ASCII) with vertices, normals, and faces.
- Frontend loads PLY via Three.js and renders it in the workspace.
- Mesh source can be scan volume or segmentation mask.
- Segmentation overlay mesh can be shown on top of scan mesh.
- Overlay opacity, iso, and step are user-controlled.
- Clipping planes can be applied to inspect internal structures.

## Mesh Tools (Current)
- Orbit, pan, and zoom controls for navigation.
- Mesh source selection (scan vs mask).
- Overlay opacity control for tumor visibility.
- Iso threshold and step controls for clarity and performance.
- Clipping plane control for sectioned views.

## Backend Upload and File Handling
- Upload endpoint: /api/uploads.
- Batch upload endpoint: /api/uploads/batch.
- Preview endpoint: /api/uploads/preview.
- Volume info endpoint: /api/uploads/volume-info.
- Volume file endpoint: /api/uploads/volume-file.
- Uploads support NIfTI, DICOM, and zip containers.
- DICOM series are converted to NIfTI on demand.
- Zip files are extracted to temp directories for preview and slicing.
- Paths are validated to allow uploads and outputs directories.

## Frontend UI and State
- App.tsx holds the main flow and state for uploads, models, and jobs.
- App.css provides all styling and animation primitives.
- Model cards show hover effects and selection state.
- Job timeline shows queued, running, done, or error states.
- Results panel displays metrics and output paths.

## Auth and Roles
- Roles: Developer, Admin, User.
- Developer controls admin and user creation.
- Admin manages users within an organization or lab.
- User is typically a clinician or operator.
- Email verification is required before first login.
- Forgot password uses email + OTP workflow.
- JWT-based auth is used for protected backend routes.

## Environment Variables to Document
- GEMINI_API_KEY (chatbot).
- GROQ_API_KEY (report analysis).
- AUTH_JWT_SECRET (backend auth).
- DJANGO_SECRET_KEY (auth service).
- DATABASE_URL / DB settings for Postgres.
- VITE_API_BASE_URL (frontend API base).
- VITE_AUTH_BASE_URL (auth service base).
- VITE_AUTH_REQUIRED (toggle auth flow).
